TAREFA T06 — Models SQLAlchemy a partir do database.sql
Prioridade P0 · limite 02:50 · depende de: T02 mergeado

OBJETIVO
Criar um model SQLAlchemy 2.0 por tabela de `database/database.sql`, espelhando EXATAMENTE as colunas, tipos, nullability, FKs, UNIQUEs (com o nome, quando o SQL dá nome, ex.: `uq_pix_transaction_transaction_id`) e CHECKs. O banco é criado pelo SQL; os models não criam tabelas (nada de create_all). Siga o padrão de model do banco/ do oberico/desafio_qitech.
Tabelas (15): pix_participant, person_type, analysis_status, decision_basis, risk_level, rule_axis, rule_outcome, account_holder, account, pix_transaction, pix_analysis, pix_analysis_axis, pix_analysis_rule, account_device, account_counterparty. A view pix_history NÃO entra nesta tarefa.
Convenções: lookups com PK `Integer` (SERIAL); tabelas de volume (account_holder, account, pix_transaction, pix_analysis, pix_analysis_axis, pix_analysis_rule, account_device, account_counterparty) com PK `BigInteger` (BIGSERIAL) e TODA FK para elas `BigInteger`; FK para lookup `Integer`. `analysis_key` é `UUID(as_uuid=True)` do dialeto postgresql com `server_default=text("gen_random_uuid()")` (NÃO é String(36)). Datas com `DateTime(timezone=True)`; dinheiro `BigInteger` nas colunas `*_minor`; `ip_address` é INET do dialeto postgresql; latitude/longitude NUMERIC(9,6); JSONB do dialeto postgresql. Os índices já existem no SQL (incluindo os covering com INCLUDE); não precisa redeclará-los no model, mas os UNIQUEs nomeados sim, com o mesmo nome. Registre os models em src/models/__init__.py na ordem de dependência (lookups → account_holder → account → pix_transaction → pix_analysis → pix_analysis_axis → pix_analysis_rule → memória) para evitar import circular.

PROTOCOLO TDD (obrigatório; o Ramon confere no PR)
- Cada ciclo tem três commits na sua branch, nesta ordem: `test(<ID>): red - <comportamento>` (só o teste novo, rodado e FALHANDO pelo motivo certo: assertion ou 404/status esperado, não erro de import ou typo), `feat(<ID>): green - <comportamento>` (o mínimo para passar; nada além do que o teste pede) e, se houver o que limpar, `refactor(<ID>): <o que mudou>` (com a suíte verde antes e depois). Não junte teste e código no mesmo commit.
- Copie a saída real do red (nome do teste + a linha do erro) e do green de cada ciclo para a descrição do PR, na seção "Ciclos TDD". Sem essa seção o PR volta.
- Um ciclo cobre um fluxo que faz sentido de ponta a ponta pela interface pública (HTTP nos testes de integração; `evaluate()` nos testes do motor): o caminho feliz, cada erro e cada borda do comportamento, não só a função isolada. Teste sem ciclo vermelho antes não vale como TDD: se um teste passar de primeira, prove que ele testa algo quebrando de propósito o código (ex.: apague a validação), mostre-o falhar e desfaça.
- Mocks só em fronteira externa. Não teste detalhe de implementação.
- Antes do PR: suíte inteira verde e `flake8` limpo.
