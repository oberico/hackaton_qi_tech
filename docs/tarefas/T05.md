TAREFA T05 — POST /pix/transaction com motor de mentira
Prioridade P0 · limite 03:00 (PR aberto) · depende de: T01 (contrato do motor, ~01:40), T02 (scaffold, ~02:10), T06 (models, ~02:50). Comece já pelos testes e pelo DTO

OBJETIVO
Construir a rota POST /pix/transaction de ponta a ponta seguindo a arquitetura em camadas do CLAUDE.md (resource → controller → repository → model; JSON Schema na porta; DTO na saída; sem camada service; nenhum raise no resource), com um MOTOR DE MENTIRA: o controller monta um `EngineResult` fixo (approved, decision_basis `clean`, eixos ok, sem regras) usando os tipos de src/engine/risk_context.py. O Ramon troca pelo motor real no T10; deixe isso isolado numa função privada do controller, fácil de substituir.
Fluxo desta tarefa (do "Fluxo do POST" do CLAUDE.md, sem as validações de sentido, que são o T12, e sem o tratamento de idempotência, que é o T09 do Ramon):
1. Schema src/schemas/post_pix_transaction.json (já existe; não altere) → 400 pelo schema_handler herdado.
2. Upsert do titular e da conta, cada um com `INSERT ... ON CONFLICT DO NOTHING` + `SELECT` pela chave natural: `account_holder` por document_number (person_type derivado do formato: CPF → individual, CNPJ → company); `account` por participante + agência + número, apontando para o titular (origem: participante `OWN_PARTICIPANT` da env; destino: `destination_account.participant`). ISPB fora da lista NÃO é erro: cria o pix_participant com `listed = false`.
3. Insert do pix_transaction: transaction_id = id do payload, payload_hash via utils/payload_hash.py, amount_minor = amount, utc_offset_minutes extraído do transaction_date, raw_payload.
4. Motor de mentira → grava pix_analysis (status_id, decision_basis_id — ambos FK de lookup —, policy_version, payer_maturity_phase, features, latency_ms medida no controller; o analysis_key é gerado pelo banco com gen_random_uuid(), leia-o de volta com RETURNING/refresh) e pix_analysis_axis (3 linhas: who/how/where, cada uma com rule_axis_id e risk_level_id) → commit.
5. Toda consulta que você escrever usa uma chave com índice (veja a tabela "Caminho de acesso" em docs/modelo-de-dados.md) e NUNCA usa o id serial como regra de negócio (nada de ordenar ou comparar por id). Se precisar de consulta nova, adicione a linha na tabela "Caminho de acesso" no mesmo PR, com o plano de `EXPLAIN`.
6. 201 {key, status, metadata}, com o metadata EXATAMENTE no formato da seção "Formato do metadata" do CLAUDE.md, montado por um DTO que lê do que foi gravado (o mesmo DTO serve ao GET e ao retry idempotente). De onde o DTO tira reasons/floors/trust/flow é a decisão D2 do TASKS.md: siga o que o Ramon responder (proposta: pix_analysis.features).
